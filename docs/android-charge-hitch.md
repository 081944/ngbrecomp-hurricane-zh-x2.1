# Android 蓄力特效与下屏状态调查

2026-11-07，在无线设备 `192.168.2.183:35903` 上调查。用户进一步确认，症状发生在蓄力特效出现时，不只在释放时。

## 已取得的现场

原安装版本 PID 12704，脱离 LLDB 时抓到：

| 时间 | 下屏快照 |
| --- | --- |
| 14:59:50.055 | mode=1，entries=0，epoch=33 |
| 14:59:50.231 | mode=3，entries=14，epoch=34 |
| 14:59:52.113 | mode=1，entries=0，epoch=35 |
| 14:59:52.305 | mode=3，entries=14，epoch=36 |

两段分别约 176、192 毫秒。mode=1 对应“进入游戏后显示背包”，没有发现同期显示屏重新创建日志。因此下屏闪回来自原生代码传了空菜单，不能称为已证明的显示连接断开。

LLDB 在 `ngb_android_quick_update` 的空菜单独立基本块实际命中 breakpoint 2.1。该构建 ELF 地址为 `0x1B390E0`，本进程 slide 为 `0x77022BC000`。现场 `x27=0`（menu）、`w5=1`（mode）；guest 状态：

```
DB9AD5=1  7F1B12=1  7F1B11=0  DB9894=3  4B7640=0
428210=4  428214=320E0  428218=6  428248=4  428250=5
DB98E4=84013800  DB5E24=18A
```

随后对 `guest_base + 0xDB9AD5` 设置硬件写入监视点，实际命中 1→0。PC 对应 `sub_00165150` 的 `loc_00165275`，生成源码 `recomp_0011.c:24275`。这是主循环比较 `DB5A68`（目标暂停计数）与 `DB5A62`（已应用计数）、恢复 task group 的路径。命中时目标计数为 0、已应用计数仍为 1。原生标志并非仅表示用户打开暂停菜单，也会覆盖特效期间的暂停。

旧 `regular_play()` 把该标志直接用于面板是否存在；于是短暂暂停会清空背包，再重新建立面板 epoch。

## 修改

`quick_select.c` 分离世界上下文和操作许可：

- `gameplay_context()` 判断是否仍处在支持的游戏世界。
- `regular_play()` 继续检查原生暂停，装备、道具、服装请求仍受原限制。
- Android 面板按上下文显示，暂停期间 `ready=0`，保留列表与 epoch。
- 原生暂停期间仍撤销待处理请求，不会把特效期间的点击延迟执行。

没有修改游戏暂停计数、特效脚本、动画速度或渲染同步。此修改直接针对下屏清空；是否同时消除主屏额外卡顿，必须实测。

## 性能记录与调试限制

已在脱离调试器期间记录 60 秒 simpleperf CPU/调度采样，972335 个样本、零丢失。`logcat` 的 NGB 日志 TID 是 log pump，并不是执行 guest 的线程，不能按日志 TID 筛选游戏调用栈。含 off-CPU 的总耗时是多线程累计值，不能当成单帧耗时。

无线条件断点仍会每帧陷入调试器，不能用于性能测量。Android 运行时的调度信号 45（`SIGRTMIN+4`）也需要透传，流程已补充到 `android-lldb-debugging.md`。暂停命中造成的无响应不属于正常运行卡顿。

增加环境开关 `NGB_QUICK_TIMING=1`，在原生暂停变化时记录可见性、操作许可、跨段帧数、持续时间、相邻帧间隔、本帧面板处理耗时及该段最大耗时。单位为微秒。仅在启用时计时；应结合无调试器实战记录评估。
